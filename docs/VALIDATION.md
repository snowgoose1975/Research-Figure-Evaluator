# 验证、证据与成品验收

当前没有实验结果。这里规定之后怎样判断完成，不能把预计结果填写成已观察事实。T04 定义口径，T06 审核系统，T07 执行固定批次和整理证据。

## 1. 最小数据与标注

第一步是 1 基础图×2版本的 dev 首件。最低候选版为 3 基础图×2版本（2 dev、1 holdout）；目标为 6×2（4 dev、2 holdout）。降低数据规模要在结果里明示，不能仍称 12 图验证。

同基础图及所有衍生版本必须同 split。holdout 在提示词、评估规则、renderer 版本冻结前不得用于优化。最终测试若暴露问题可以修，但原结果保留，该套图之后不能继续声称完全未见；需要新保留图或明确 exploratory。

每张基础图先有语义 gold、3–5 个原子 K、图内图例、来源/许可、split、审核人和版本配方。制图模型可以批量执行，gold 与“改动没有改变语义”的判断由强模型/玉米审核。未经审查的自然语言自生成答案不作 gold。

样例类型依次覆盖：促进/抑制/方向；条件和作用范围；证据状态与虚实线；分组、反馈和拥挤。首版只在受支持单面板范围内增加复杂度。

清晰度成对对照只改一个表达因素且语义不变。把抑制改成促进属于“图与意图不一致”，另列测试。预期误读仅是待检验假设，不保证问题版一定让模型失败。

## 2. 必需检查

| 检查 | 方法 | 通过条件 |
|---|---|---|
| Schema | 正例和非法引用/ID/bbox/容量反例 | 无静默截断、补义或空结果回退 |
| 输入隔离 | 捕获实际 adapter 参数/消息，检查白名单 | A 无 K；renderer 无原图；B 仅 PNG；无历史答案或带答案文件名 |
| Renderer 正控 | 人工 Memory→SVG/PNG，不依赖 A | 每种符号/条件/证据/分组可见，条目审计准确；强模型视觉复核 |
| 读取能力 | 已知记忆的重建图→B | 单列 B 对标准绘图的恢复情况；不是原图质量成绩 |
| 评价规则 | T04 的 golden 判例 | 不把影响当促进，不忽略条件/证据，不用局部 ID 直接对齐 |
| 一次真实链路 | 一对 dev 图真实 A→render→B→评价 | 保存真实响应、PNG、审计、逐项结果与用量；完成不要求结果符合预期 |
| 失败路径 | 网络超时、解析失败、unsupported、进程中断 | 明确阶段、产物保留、重试有限、无伪成功 |
| 修改版对比 | 固定 K、模型、prompt、参数和 renderer | 仅图变化时标可比，其余差异如实列出 |
| 页面 | 上传至导出全部主要状态 | 用户能理解结果、查看证据、识别 mock/replay/失败 |
| 隐私与分享 | 检查导出、服务响应、待提交清单 | 不含密钥、私有磁盘路径、未经许可图稿或保留集答案 |

程序审计只确认绘制实现覆盖字段，不保证视觉可读；截图人工检查不可省略。存在 renderer 缺口时，不把 B 的相关差异判为原图导致。

## 3. 对照与指标

每个 K 分别报告 K→A 和 K→B 的 status/issue/依据；A→B 对齐全部 A 已提取事实；M→rendered 报表达覆盖和警告。

两种基线同时保留：

- **A-only**：不增加调用，以 A 对关键点的恢复作为盲读基线。
- **direct-check**：独立模型调用直接看到原图和关键点，输出有依据的逐项检查。它是用户最省事替代方案，已知目标的信息优势必须写明；不得回流主流程。

原方案中的 direct-check 不必假装与盲读任务相同。对照问题是：往返流程是否发现额外可行动问题，重建图是否帮助解释，付出了多少延迟/成本，并引入多少额外误差。不能只比较“哪个 AI 同意 K 更多”。

记录完整保留数/全部已确认 K、不确定数、错误分类数量、B 新增未匹配断言数、renderer 警告数、有效运行数/尝试总数、延迟与实际用量。新增未匹配不等于已证明幻觉。

如果人工 gold 判断模型误报，也记录误报；若要计算 precision/recall，需要先冻结“问题”标注定义和分母，由 T04 审核，不能直接把 K→A 的恢复比例叫准确率。

## 4. 批次与稳定性

1. 固定代码/prompt/schema/renderer/模型配置，验证 1 对 dev 首件，再测 direct-check；真实 API 最少先跑通一次，避免大批消耗后发现协议错误。
2. 最低候选版：6 个图片版本各一次主链路和 direct-check，可复用同配置首件记录；不要重复计数。
3. 演示用 dev 图对每版目标共 3 次主链路，至少一次额外重复才能讨论初步波动；资源不足时报告实际次数。direct-check 重复次数明确记录，次数不对称不作严格统计优劣宣称。
4. 有余量扩到 12 图，先排除 pipeline 故障；holdout 只在冻结版本后执行。

示意调用量：6 图片×（A+B+direct）约 18 次视觉调用；12 图片约 36 次；重复、重试和语义助手另外计算。这是调用次数预算，不是费用估计，需按真实模型计费实测。T07 只能执行批准的有限清单，不能一直刷到出现理想结果。

每次运行记录模型实际返回的 ID/版本、参数、时间、输入 hash、K/config digest、代码版本、尝试次数及用量。同模型独立会话不保证错误独立；少量重复不能证明普遍稳定。

## 5. 失败、人工介入与回放

- 按全部尝试报告流程成功/失败，失败按阶段分类；有效运行的语义结果另列，不能把 API 错误当漏读，也不能把它从总体记录删掉。
- 人工纠正仅做额外 overlay，注明修改者、理由和原记录，不覆盖原模型结果。
- 改 prompt/schema/参数/图稿/K 就产生新版本与关联。失败重试也保留 attempt，不让成功重试抹去失败。
- 演示选用 dev 案例，说明选择方式；holdout 全部结果列出，不只挑效果好的一张。
- 真实历史回放显示 replay 标签、原时间、模型和 run ID。没有真实结果可回放时，只能叫 mock，不造成功记录。

## 7. 演示结构与提交包

2 分钟核心版建议：15秒问题和领域场景→20秒图与 K→40秒记忆/重建/逐条差异→25秒同配置改版对比→20秒对照、限制和可复现入口。若未观察到提升，就展示观察到的变化，不伪造成功叙事。

≤4分钟完整版补充：renderer 正控、基线、全部小样本结果、一次失败/不确定及下一步。时长上限与正式入口提交前再按官方公告确认，见 [COMPETITION](COMPETITION.md)。

`docs/submission/` 应含一页英文稿、两版视频脚本、待发布帖子文本、仓库/运行说明、演示 run 清单、来源许可和提交检查表。它们先是草稿；实际发帖、部署、push 和正式提交仍须玉米许可。
